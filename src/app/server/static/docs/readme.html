项目简介

FN软仓服务端是 FN软仓的管理后端。除提供 FN软仓自己的官方源给软仓客户端外， 还具有公告管理、三方源管理、应用明细查看、仪表盘统计、应用编辑、应用上传、 访问限速、外链加速、以及开发者聚合系统等功能。

v2.10.0 核心架构升级：开发者正式入驻后，不再需要维护外部的 Gitee/GitHub 仓库。应用数据直接托管在源主服务器的 data/dev-sources/ 目录下。同时新增了基于设备的精准活跃统计。

三种参与方式

方式一 · 纯在线托管（v2.10.0 推荐）

开发者不需要懂 Git，不需要建仓库，不需要写 JSON。向源主申请开通后，直接在网页后台填写应用信息。

1
申请入驻
在软仓客户端或网页端提交入驻申请。源主审核通过后，发送专属管理后台链接。
2
在线填表
在后台点「添加应用」，拖入 FPK 文件自动解析，填入下载直链。
3
提交审核
点击「保存并提交审核」。源主通过后，客户端 30 秒内可见。

方式二 · 自带 fnrc.json（极客传统模式）

如果你有多个应用，或者希望数据完全独立，可以手写一份 fnrc.json 并挂载在 Gitee/GitHub 上，然后将直链交给源主添加为“三方源”。

此模式下一次审核后，后续更新只需修改 Gitee 里的 JSON 并 push，无需再找源主审核，服务端每 5 分钟会自动检测更新。

方式三 · 自建独立源（成为源主）

通过 Docker 部署 FN软仓服务端，自己当源主，建立自己的生态圈。 你可以自己上传应用，也可以将别人的 fnrc.json 或其他的 FN软仓服务端作为上游源聚合进来。

部署步骤

1. 准备环境

  • Docker 已安装
  • 一个公网可访问的地址（域名或 IP）
  • 安全组 + 防火墙放行 5660 端口

2. 准备数据目录

mkdir -p /vol1/1000/fn-appstores-server/data/{apps,icons,previews}

3. 启动服务端

docker run -d --name fn-appstores-server --restart unless-stopped \
  --network host \
  -e TZ=Asia/Shanghai \
  -e BASE_URL="http://你的域名或IP:5660" \
  -e ADMIN_PASSWORD="你的管理密码" \
  -e NOTICE_PASSWORD="公告员密码" \
  -e AUTO_CLEAN_DEV_UPSTREAM="false" \
  -v /你的数据目录:/app/data \
  ccr.ccs.tencentyun.com/hhxs2025/fn-appstores-server:2.10.0

4. 验证

curl http://127.0.0.1:5660/health
注意：BASE_URL 必须含端口，否则图标、截图、下载地址全都不可达。

5. 访问管理后台

http://你的地址:5660/admin

开发者系统（v2.10.0 新流程）

纯在线模式，彻底告别 Gitee 依赖。
开发者通过客户端或网页提交入驻申请 -> 源主一次审核开号 -> 开发者在线填表保存 -> 源主二次审核应用 -> 上线。整个过程无需接触任何外部代码仓库。

入驻流程

  1. 开发者在申请页填写源名称和联系方式提交。
  2. 源主在 /admin-review 的「入驻申请」Tab 通过审核。
  3. 系统自动生成 token 和空源，源主复制后台链接发给开发者。

应用审核流程

开发者在后台填完应用信息点击保存后，会进入 Pending（待审核） 状态。 源主在 /admin-review 的「应用审核」Tab 看到变更记录。通过后，应用立即出现在客户端。

严格审核机制：由于源主负责托管开发者的数据，为了平台安全，开发者每次新增应用、修改版本、下架应用，都必须经过源主审核。

被拒绝后

  • 开发者在后台对应的应用卡片上会看到红色的「被拒绝」标签及具体原因。
  • 修改后重新点击保存即可再次提交审核。

从 2.9.x 升级到 2.10.0

# 1. 备份数据目录
cp -a /你的数据目录 /你的数据目录_bak_$(date +%Y%m%d)

# 2. 停旧容器并删除
docker stop fn-appstores-server
docker rm fn-appstores-server

# 3. 拉新镜像
docker pull ccr.ccs.tencentyun.com/hhxs2025/fn-appstores-server:2.10.0

# 4. 用原数据目录启动（同上一条 docker run）
自动迁移机制：
  • 服务端首次启动 2.10.0 时，会自动扫描旧的 dev-accounts.json 和 upstream.json。
  • 系统会自动拉取开发者曾经在 Gitee 上的 fnrc.json，并将数据持久化保存到本地的 data/dev-sources/ 目录下。
  • 迁移完成后，旧的 upstream 记录将被清理或禁用，系统全面转向本地托管。

常见问题

Q1：客户端看不到新应用？

如果是新上传的，去后台点「刷新应用缓存」；如果是刚审核通过的，等待 30 秒（客户端有缓存），或让用户在客户端清除本地缓存。

Q2：三方源显示「离线」？

检查 URL 是否可访问（末尾别加 /），点「测试」看具体错误。连续失败 3 次的源在拉取时会被自动跳过。

Q3：设备统计里的「兜底」是什么意思？

新版客户端请求时会带上专属 ID，显示为绿色的「准确」。老版本客户端没有专属 ID，服务端只能用“IP+浏览器UA”进行哈希计算来近似识别，因此显示为黄色的「兜底」。建议尽快升级客户端。

Q4：如何配置应用的多架构（x86 / ARM）？

在开发者后台添加应用时，保持两条记录的「应用 ID」相同，但「适用架构」分别选择 x86 和 arm。客户端会自动根据用户的设备架构展示对应版本。

Q5：还需要配置 Gitee 仓库吗？

不需要。 v2.10.0 彻底取消了对外部 fnrc.json 的强制依赖。开发者只需在后台网页上填写应用直链（直链依然可以是 Gitee Release 或 GitHub Release）。

Q6：自建服务端如何对接官方源？

在后台「三方源管理」中，添加官方源的地址，或者你自己的 Gitee fnrc.json 地址。这样你的客户端就能同时看到你上传的应用和官方源的应用。
