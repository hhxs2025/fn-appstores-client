项目简介

FN软仓服务端是 FN软仓的管理后端。除提供 FN软仓自己的官方源给软仓客户端外， 还具有公告管理、三方源管理、应用明细查看、仪表盘统计、应用编辑、应用上传、 访问限速、外链加速、开发者聚合系统等功能。

优势：任何人拿走服务端，改个 BASE_URL 环境变量就能另起炉灶。 Go + Docker，镜像约 15MB，内存约 10MB，支持全托管 / 半托管自由组合。

两种参与方式

方式一 · 自建服务端（做源主）

你搭一个服务端，自己收录、自己分发。用户主动添加你的源地址，就能看到你的应用。 自己当源主。

1
部署
Docker 一条命令拉起服务端，镜像约 15MB。
2
上架
后台拖入 FPK，或使用外链托管（FPK 走 Gitee / GitHub / OSS）。
3
分享
把源地址发给朋友或公开。

方式二 · 开发者聚合（把应用交给官方源）

你不用搭服务器，只要提供一份 fnrc.json，就能把应用聚合到源主的源里， 该源的所有用户都能看到。

v2.9.3 起流程大幅简化：从"进群 → 等源主开号 → 填应用 → 再申请聚合"， 变成"公开填表 → 一次审核 → 拿 token 直接用"。

1
公开申请
打开 /dev/apply，填源名称 + fnrc.json 直链 + 联系方式，提交。 如果还没有 fnrc.json，申请页顶部提供两种生成方式：
  • 下载空模板：改几个字段就能用
  • 在线生成器：图形化表单，填几个字段就能生成 JSON，零基础也能用
生成的文件推到 Gitee 后，回到申请页提交即可。
提交成功后会拿到一个 申请编号，请截图保存。
2
等源主审核
源主在 /admin-review 的「待审申请」Tab 处理。 通过后，源主会通过你填写的联系方式发来开发者后台入口。 如果长时间没收到，可以凭申请编号在 /dev/apply 的「查询进度」Tab 自行查询。
3
进入开发者后台，应用已自动聚合
打开源主发来的链接（形如 /dev/manage?token=xxx），你的应用此时已经被自动聚合， 客户端 5 分钟内可见。
后续更新不需要再审核：改应用 → 导出 fnrc.json → push 到仓库 → 自动生效。
推荐组合：fnrc.json 放 Gitee raw（更新立即生效，URL 不变，无需重审）， FPK 放 GitHub Release（走加速器）。两者独立。
fnrc.json 直链可以是 Gitee raw，也可以是 Gitee / GitHub Release 附件， 只要 URL 以 .json 结尾、浏览器点开直接显示 JSON 内容即可。 用 Release 附件时注意：每次发新 release 会改变 URL，需要走「申请聚合」提交换 URL 请求。

部署步骤

1. 环境准备

  • Docker 已安装
  • 一个公网可访问的地址（域名或 IP）
  • 安全组 + 防火墙放行 5660 端口

2. 准备数据目录

mkdir -p /vol1/1000/fn-appstores-server/data/{apps,icons,previews}

3. 启动服务端

docker run -d --name fn-appstores-server --restart unless-stopped \
  --network host \
  -e TZ=Asia/Shanghai \
  -e BASE_URL="http://你的域名或IP:5660" \
  -e ADMIN_PASSWORD="你的管理密码" \
  -e NOTICE_PASSWORD="公告员密码" \
  -v /你的数据目录:/app/data \
  ccr.ccs.tencentyun.com/hhxs2025/fn-appstores-server:2.9.3

4. 验证

curl http://127.0.0.1:5660/health
注意：BASE_URL 必须含端口，否则图标、截图、下载地址全都不可达。

5. 访问管理后台

http://你的地址:5660/admin

开发者系统（v2.9.3 新流程）

v2.9.3 起：开发者注册 + 聚合申请已合并为一次审核。
开发者通过公开入口自助提交申请 → 源主一次审核 → 自动创建开发者账号 + 自动写入上游源 + 自动回填应用。

申请入口

访问 http://源地址:5660/dev/apply(此处不给FN软仓主源地址是因为你也可以跑服务端)，页面有两个Tab：

  • 提交申请：填写源名称 / fnrc.json 直链 / 联系方式
  • 查询进度：凭申请编号查询审核状态

fnrc.json 生成器

申请页顶部有一个折叠面板「📄 还没有 fnrc.json？展开查看」，提供两种方式：

方式适合特点
下载空模板 懂 JSON 的人 下载预填好结构的 JSON，改几个字段即可
在线生成器 零基础开发者 图形化表单：填字段 → 生成 JSON → 下载/复制

生成器表单字段：源名称、应用 ID / 名称 / 版本 / 下载地址 / 图标 URL（必填）、 适用架构、标签（点选式，最多 2 个）。可以点「+ 添加应用」增加多条，支持多架构。

生成的 JSON 不会上传到服务端。生成器是纯前端功能， 所有数据在浏览器本地拼装成 JSON，只通过「下载」/「复制」交给开发者自己。开发者需要自己 push 到 Gitee 仓库， 然后回申请页填 URL。

申请提交后

  1. 服务端实时拉取你填的 JSON URL，校验能否访问 + 能否识别应用数
  2. 校验通过 → 写入 dev-apply-requests.json，状态 pending
  3. 返回申请编号（形如 apply_1729186041253）
  4. 源主到 /admin-review 的「待审申请」Tab 处理
  5. 通过 → 自动生成 token + 自动写 dev-accounts.json + 自动写 upstream.json + 自动回填应用
  6. 源主弹窗显示通知文案 + 后台入口链接，复制后发给开发者
  7. 开发者凭 token 进 /dev/manage，应用已被自动聚合

被拒绝后

  • 开发者凭申请编号到 /dev/apply 的「查询进度」Tab 自行查询，能看到拒绝原因
  • 被拒后可以重新提交同一 JSON URL，系统会复用原记录，状态改回 pending
  • 源主也可主动联系（用开发者填写的联系方式）

开发者后台功能

  • 拖入 FPK 自动解析：提取 ID / 名称 / 版本 / 类型 / 架构 / 描述 / 作者 / 反馈入口 / 标签
  • 上架 / 下架开关：每个应用卡片右上角，下架的应用不会出现在导出的 fnrc.json 里
  • 预览 fnrc.json：导出前自查，弹窗显示生成的 JSON + 校验结果（错误 / 警告 / 提示三级）
  • 通知中心：右上角铃铛，显示审核通过 / 拒绝通知，带未读红点 + 数字角标
  • 数据看板：今日 / 本周 / 累计下载量 + 评分
  • 申请聚合：填 fnrc.json 公开 URL，提交审核（仅换 URL 时需要）

源主后台管理

位置作用
/admin-review「待审申请」Tab 处理开发者首次公开申请（自动开号 + 自动聚合）
/admin-review「聚合审核」Tab 处理已通过开发者的URL 变更 / 重新提交
后台「开发者管理」Tab 手动创建开发者、复制访问链接、重置 token、删除开发者
后台「三方源管理」Tab 禁用 / 删除聚合源

从 2.9.2 升级到 2.9.3

# 1. 备份数据目录
cp -a /你的数据目录 /你的数据目录_bak_$(date +%Y%m%d)

# 2. 停旧容器
docker stop fn-appstores-server
docker rm fn-appstores-server

# 3. 拉新镜像
docker pull ccr.ccs.tencentyun.com/hhxs2025/fn-appstores-server:2.9.3

# 4. 用原数据目录启动（同上一条 docker run）
兼容性：新增数据文件 dev-apply-requests.json 首次启动时自动生成， 现有数据全部保留。
自建镜像时必须 docker compose build --no-cache，避免 Docker 复用旧镜像层。
从 2.9.2 升级注意事项：
  • 版本号常量已从 2.9.2 升级到 2.9.3
  • 加速器健康检查样本池改为「Owner/Repo/Tag/File 拆分」结构，升级版本只需改 Tag 和 File 字段
  • 修复了多架构上传互相覆盖的问题，升级后同 ID 的 x86 / ARM 版本会分别存为带 platform 后缀的文件
  • 修复了 fnrc.json 空 apps 数组被误判为离线的问题
  • 修复了开发者审核中途失败导致重复创建账号的问题

常见问题

Q1：客户端看不到新应用？

后台点「刷新应用缓存」+ 客户端「设置 → 清除本地缓存」。

Q2：三方源显示「离线」？

检查 URL 是否可访问（末尾别加 /），点「测试」看具体错误。

Q3：加速器为什么有时客户端下载很慢？

检查加速站是否真的可用。后台「外链加速」→ 站点级测试，或点「立即检测一次」看健康状态。 加速站会有"较慢"档徽章，可区分"能用但慢"和"挂了"。

Q4：fnrc.json 更新多久生效？

Gitee raw：60~300 秒。
Gitee / GitHub Release 附件：无 CDN 缓存，但需发新 release 才算更新。
jsDelivr：最长 12 小时（可访问 purge.jsdelivr.net 强制清）。

Q5：审核后还要再审核吗？

不用，一次性审核。之后开发者自主更新应用，直接改 fnrc.json + push 即可。

Q6：三方源管理里出现两条一样的源？

大概率是孤立记录。到「三方源管理」里删掉那条"离线很久"的即可。
出现原因：先删 /admin-review 记录，再让开发者重新申请。正确做法是不删审核记录， 让开发者走「申请聚合」提交换 URL 请求。

Q7：开发者完全不懂 JSON，能上架吗？

能。申请页顶部的「在线生成器」就是给零基础开发者用的： 填几个字段（源名称、应用 ID、名称、版本、下载地址、图标），点一下按钮就能生成可用的 fnrc.json。 生成器是纯前端功能，数据不上传服务端。

Q8：拒绝了开发者的公开申请，对方怎么知道？

不会主动通知（公开申请阶段还没有 token，也没有站内通知渠道）。
但开发者可以凭申请编号到 /dev/apply 的「查询进度」Tab 自行查询到拒绝状态和原因。
源主也可以主动联系开发者（用他填写的联系方式）。

Q9：fnrc.json 直链可以用发行版附件地址吗？

可以，只要 URL 以 .json 结尾、浏览器点开直接显示 JSON 内容。
支持：

  • Gitee raw：https://gitee.com/用户名/仓库/raw/master/fnrc.json
  • Gitee Release 附件：https://gitee.com/用户名/仓库/releases/download/v1.0.0/fnrc.json
  • GitHub Release 附件：https://github.com/用户名/仓库/releases/download/v1.0.0/fnrc.json
不推荐：
  • Release 页面地址（返回 HTML 页面而非 JSON）
  • raw.githubusercontent.com（国内经常掉线）

Q10：多架构应用上传会互相覆盖吗？

不会。v2.9.3 起，上传 x86 / ARM 版本时会分别存为带 platform 后缀的文件名 （如 myapp-1.0.0-x86.fpk 和 myapp-1.0.0-arm.fpk），互不影响。 升级前的旧版本上传方式会互相覆盖，建议升级到 2.9.3。
